# GitHub 凭据换新实录（2026-10-28）：换一个 token 牵出四个坑

> 本文记录 2026-10-28 更换 GitHub Personal Access Token 的全过程。起因只是一次例行换新——旧凭据迟早失效，生成个新的替换掉，复制粘贴的活儿。
>
> 结果这条链路上一共挖出四个坑：**探针会说谎、权限有盲区、本地早就落后、OAuth 被当成 PAT**。四个都不致命，但每一个都会在某一天悄悄发作，而发作时你多半不会第一时间意识到是 token 的问题。
>
> 全文按「怎么发现的 → 怎么处理的 → 沉淀成什么」推进。如果只想拿走可复用的部分，直接跳到第六节。

---

## 一、起因：新 token 到手

新生成的 token 信息如下：

| 项目 | 值 |
|---|---|
| 名称 | `workbuddy-automation-2026` |
| 类型 | Fine-grained personal access token |
| 权限 | Actions 读写、Contents 读写、Issues 读写、Metadata 只读 |
| 作用范围 | 2 个仓库（博客仓库 + 类比修辞库） |
| 到期 | 2027-10-28 |

第一时间做了两件顺手的事：设两个到期提醒（到期前 30 天预警 + 到期前 7 天兜底），然后验证连通性。

验证的起因很朴素：**"生成成功"不等于"能用"**。生成页面不会告诉你它能不能推代码、能不能被 Actions 调用。

---

## 二、第一个坑：ls-remote 是个会说谎的探针

先扫了一遍基础配置，全部正常：

| 检查项 | 结果 |
|---|---|
| 远程地址 | 两个仓库均为 HTTPS，正确 |
| 代理配置 | git 的 http/https.proxy 已指向本地代理 |
| 凭据助手 | `credential.helper = manager` |
| `git ls-remote` | 两个仓库均成功 |

看起来一片绿。**但最后那条是假信号。**

`git ls-remote` 对**公开仓库**匿名也能成功——它只读取远端引用，不校验身份。拿它当"token 有效"的证据，等于拿"门牌号在"证明"你有钥匙"。

真正的认证验证得打到 API 上：

```bash
curl -H "Authorization: Bearer $TOKEN" https://api.github.com/user
```

返回 `200` 且 `login` 是本人，才是有效 token。

顺带一个反直觉的判据：**`git push --dry-run` 报 non-fast-forward（让你先 pull），恰恰说明认证通过了**。权限不足会直接 403/401，不会走到内容比较这一步。所以：

- 报 `non-fast-forward` → 认证 OK，只是内容落后；
- 报 `Permission denied` / `403` → 才是真的没权限。

## 三、落地：把换 token 固化成脚本

既然要换，就换得彻底一点。写了 `swap-github-token.sh`，一条命令跑完五步：

```bash
bash swap-github-token.sh <新token>
```

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1 | 打 API 验证身份，非本人则中止 | 中止，不写入 |
| 2 | 写入系统凭据管理器 | — |
| 3 | 验证两仓库连通 | 报告 |
| 4 | 加密更新两个仓库的 Actions secret | 报告，不回滚 |
| 5 | 复查凭据残留 | 提示手工处理 |

把身份校验放在最前面，是为了杜绝"把错 token 写进去"这种最坏情况。

第 4 步是唯一有技术含量的部分。GitHub 不允许明文传输 secret，必须先用仓库公钥做**密封加密**（libsodium SealedBox），再 PUT 上去：

```python
from nacl import encoding, public as nacl_public

# 1. 取仓库公钥
pk = get_public_key(repo)                      # GET /repos/{repo}/actions/secrets/public-key
# 2. 用公钥密封加密
sealed = nacl_public.SealedBox(
    nacl_public.PublicKey(pk["key"].encode(), encoding.Base64Encoder())
)
enc = base64.b64encode(
    sealed.encrypt(token.encode(), encoder=encoding.Base64Encoder())
).decode()
# 3. 写入
put_secret(repo, secret_name, enc, pk["key_id"])  # PUT /repos/{repo}/actions/secrets/{name}
```

第 1、2、3、5 步都过了。**第 4 步死了，403。**

## 四、第二个坑：403 暴露的权限盲区

```
Contents → 200 OK
Actions  → 200 OK
Secrets  → 403 Forbidden
          "Resource not accessible by personal access token"
```

原因：这个 token 只勾了 Actions / Contents / Issues / Metadata 四项。**Secrets 是一个独立权限项，不在 Actions 权限的覆盖范围内。**

这一条挡住的是两个仓库里各挂着的自定义 secret：

| 仓库 | secret | 用途 |
|---|---|---|
| 博客仓库 | `METRO_SYNC_TOKEN` | 客流数据工作流推送代码 |
| 类比修辞库 | `BLOG_REPO_PAT` | 同步内容到博客仓库 |

这两个 secret **必须在，且必须是 PAT**——这是工作流里最容易踩的设计陷阱：

> Actions 默认的 `GITHUB_TOKEN` 发起的 push **不会级联触发其他工作流**。也就是说，如果用 `GITHUB_TOKEN` 推送，数据更新了，但 `deploy.yml` 不会被唤醒，站点就永远不刷新。**只有用 PAT 推送，才能让"数据更新 → 自动部署"这条链跑通。**

工作流文件里甚至专门留了这句注释：

```yaml
# 必须使用 PAT：GITHUB_TOKEN 发起的 push 不会级联触发其他工作流
token: ${{ secrets.METRO_SYNC_TOKEN }}
```

所以这两个 secret 里存的 token 不能失效，一失效就是静默故障：Actions 还是绿的，数据却不再更新。

**决策：不重新生成 token。**

理由很简单——重新生成的目的是拿到 Secrets 权限，而拿它只为省掉一次网页粘贴。既然旧 token 目前还活着，就没有必要为了"能自动改"而多管理一个 token。直接在网页把两个 secret 的值换成新 token，3 分钟，且顺带把 secret 的生命周期对齐到了 2027-10-28。

换完做端到端验证，两个工作流都支持手动触发（这点很关键）：

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -d '{"ref":"main"}' \
  https://api.github.com/repos/{owner}/{repo}/actions/workflows/{wf}.yml/dispatches
```

两个都返回 204、执行结果 success。其中最有用的一步是类比修辞库的 `Commit and push`——它用 `BLOG_REPO_PAT` 去 checkout 另一个仓库，这个 secret 只要失效，这里立刻 401。

## 五、第三个坑：本地早就落后了 9 个提交

`push --dry-run` 那次 non-fast-forward 顺手暴露了这件事：

| 仓库 | 落后 | 来源 |
|---|---|---|
| 博客仓库 | 9 个提交 | Actions 自动同步 + 客流数据 |
| 类比修辞库 | 1 个提交 | 页面同步 |

**根因是机制性的**：Actions 在云端推送提交，本地对这些提交一无所知，于是本地副本被越甩越远，直到某天你想推送时才撞上。

处理方式取决于工作树状态：干净就 `git pull --ff-only` 拉平，有本地改动则 `git pull --rebase`。

还顺手修了一个隐患：博客仓库的 `master` **没有绑定上游分支**，`git pull` 会直接报 `no tracking information`。补上即可：

```bash
git branch --set-upstream-to=origin/master master
```

## 六、第四个坑：`gho_` 不是 PAT

换完去 Personal access tokens 页面想 revoke 旧 token，**翻遍了 classic 和 fine-grained 两页都找不到**。

原因在 token 前缀上：

| 前缀 | 类型 | 显示在哪个页面 |
|---|---|---|
| `ghp_` | Classic PAT | Personal access tokens (classic) |
| `github_pat_` | Fine-grained PAT | Fine-grained tokens |
| **`gho_`** | **OAuth token** | **上面两页都不显示** |

那个旧凭据是 `gho_` 开头，是 **OAuth token**——通常由 Git Credential Manager 在登录时通过 OAuth 流程自动签发并存入系统凭据管理器，不是手动创建的，所以在 PAT 页面当然没有。

它的撤销入口在另一处：

> Settings → Applications → **Authorized OAuth Apps** → Git Credential Manager → Revoke

撤销完必须复验——这是不可逆操作。果然不止 `ls-remote` 和 `push --dry-run`，还做了一次**真实写入测试**：

```bash
git checkout -b tmp/token-verify
git commit --allow-empty -m "chore: 验证写入能力"
git push origin tmp/token-verify      # 成功 → 远端确实收到了
git push origin --delete tmp/token-verify   # 清理远端
git branch -D tmp/token-verify              # 清理本地
```

刻意用临时分支，是为了**不触碰 `master`/`main` 从而避免误触发部署**。测完远端本地都删干净。

结论：撤销 OAuth 没有伤到任何东西。本机 git 靠凭据管理器里存的 PAT 独立工作，不再依赖 OAuth 通道。

**但有个遗留影响要记住**：OAuth 撤销后，将来 PAT 失效时 GCM 不会再自动跳浏览器授权，只能手动写入新 PAT。所以换 token 脚本成了唯一入口。

## 七、沉淀：可复用检查清单

换 token 这件事，按顺序过一遍：

| # | 检查项 | 判据 | 常见假信号 |
|---|---|---|---|
| 1 | 远程地址与代理 | `git remote -v` + `git config http.proxy` | — |
| 2 | token 有效性 | API `/user` 返回 200 且 login 正确 | ❌ `ls-remote` 匿名也能过 |
| 3 | push 权限 | `push --dry-run` 报 non-fast-forward | ❌ 403 才是真没权限 |
| 4 | 本机凭据 | `git credential fill` 返回值是新 token | — |
| 5 | Actions secret | 工作流手动触发后 success | ❌ 无变更时 push 步骤会 skipped |
| 6 | 本地同步 | `rev-list --count HEAD..origin/分支` | ❌ `status` 用的是本地缓存的 remote ref |
| 7 | 旧凭据清理 | 区分 `ghp_` / `github_pat_` / `gho_` | ❌ OAuth token 不在 PAT 页面 |

三个值得单独记住的判断：

1. **公开仓库的 `ls-remote` 不能证明任何事。**
2. **想让 Actions 的 push 级联触发部署，就必须用 PAT，不能用 `GITHUB_TOKEN`。**
3. **Secret 的读写是独立权限，勾了 Actions 权限也不包含它。**

## 八、还没闭环的一件事

这次验证留了个尾巴：两个工作流因为都没有实际内容变更，`提交变更`/`拉取并推送` 两步是 **skipped** 的，部署工作流也没被唤醒。

所以「**用 PAT 真实推送一次并级联触发部署**」这条最关键的链路，当天没有被实锤。

逻辑上是闭合的（secret 里放的就是本机刚验证过能推送的同一个 token），但逻辑闭合不等于实证。这条留给 11-04 那次客流跑批自然验证——届时核对三件事：推送步骤是 success 而非 skipped、部署工作流是否被 push 事件唤醒、本地是否拉平。

三个时间点也就此排好：

| 时间 | 事项 |
|---|---|
| 2026-11-04 | 首次真实推送 + 部署级联验证 |
| 2027-09-28 | 到期前 30 天预警（脚本一键换新，记得勾 Secrets 权限） |
| 2027-10-21 | 到期前 7 天兜底 |

## 附：换 token 脚本

完整脚本见仓库 `swap-github-token.sh`，核心的五步流程：

```bash
#!/usr/bin/env bash
# 用法：bash swap-github-token.sh <新token>
set -u
TOKEN="${1:-}"

# 1. 验证身份，非本人直接中止（避免写错 token）
LOGIN=$(curl -s -H "Authorization: Bearer $TOKEN" https://api.github.com/user \
        | grep -o '"login": *"[^"]*"' | head -1 | cut -d'"' -f4)
[ "$LOGIN" = "你的用户名" ] || exit 2

# 2. 写入系统凭据管理器
printf 'protocol=https\nhost=github.com\nusername=你的用户名\npassword=%s\n\n' "$TOKEN" \
  | git credential approve

# 3. 验证两仓库连通
git -C "$REPO" ls-remote --heads origin

# 4. 密封加密更新 Actions secret（Python + PyNaCl）

# 5. 复查残留
git credential fill | grep '^password='
```

> **提醒**：换 token 的脚本里包含明文凭据，请放在仓库外或非公开位置，别跟着本文一起公开。
