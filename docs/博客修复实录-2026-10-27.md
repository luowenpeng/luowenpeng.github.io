# 个人网站修复实录（2026-10-27）：从一次 404 事故说起

> 本文记录 2026-10-27 一天里对个人网站 `luowenpeng.com` 做的一次完整体检与修复。起因只是一个问题：**这个仓库和线上站点之间的联系，真的健康吗？** 顺着这条线索查出 16 处问题、修复 12 处，中途亲手把站点搞挂了约 20 分钟，最后把经验固化成一份可复用的检查清单。
>
> 前半部分是技术修复记录，后半部分是事故复盘与经验沉淀。如果只关心「下次别再踩什么坑」，可以直接跳到第五节。
---

## 一、起因：一个「看起来很健康」的问题

最初想确认的事很朴素：仓库 `luowenpeng/luowenpeng.github.io` 和线上站点之间，是不是真的严丝合缝。于是把仓库全量克隆下来逐文件读，同时对照线上做了几十次实测。

验收结果出人意料地干净：

| 校验项 | 结果 |
|---|---|
| 部署是否反映最新提交 | ✅ 10:16 推送，10:51 线上已更新 |
| 仓库 md 文件 vs sitemap | ✅ 42 篇 md + 2 个独立页 = 44 条 URL，无孤儿无缺失 |
| config.ts 导航与侧边栏链接 | ✅ 无一条指向不存在的文件 |
| md 内部链接与图片 | ✅ 无断链、无缺图 |
| RSS | ✅ 36 条，与「42 − 首页 − 5 专题」完全对得上 |

**结论是：链路连通，但连通之后的质量在漏。** 站点能访问、文章能打开、部署能自动跑，这些容易验证的部分全对；真正出问题的是那些「不影响你打开页面，但影响别人怎么看到你」的地方——分享卡片、RSS、统计、HTTPS。

## 三、修复过程

### 3.1 按页生成 OG 卡片

问题根源在 `config.ts` 的全局 `head`：写死进去的 `og:title` 会**覆盖**每篇文章自己的元信息。VitePress 的 `transformHead` 钩子正是为此设计的，它按页面调用，能拿到 `pageData.frontmatter`。

做法分两步：删掉全局 head 里那 7 行写死的 og/twitter 标签，改由钩子逐页生成：

```ts
transformHead({ pageData }) {
  const fm = pageData.frontmatter
  const isHome = pageData.relativePath === 'index.md'
  const url = pageUrl(pageData.relativePath)
  const title = fm.title ? `${fm.title} | ${SITE_NAME}` : `${SITE_NAME} — ${SITE_TAGLINE}`
  ...
}
```

顺带补上了三样原本没有的：`canonical`（防止重复内容）、`article:published_time`、`og:locale`。

其中 `pageUrl()` 要自己处理中文路径编码——站点用了中文文件名做 slug，直接拼接会得到非法 URL：

```ts
const path = relativePath.replace(/\.md$/, '').split('/').map(encodeURIComponent).join('/')
```

> **验证**：修复后抓线上第 43 期周报页，`og:title` 为「城轨周报 · 第 43 期 | Wenpeng LUO」，`og:description` 为该期摘要——与页面 `<title>` 一致了。

### 3.2 RSS 的三处缺陷

同一次修复里连着处理了三处：

1. **自动发现**：在 head 加一行 `<link rel="alternate" type="application/rss+xml" href="/feed.xml">`。
2. **xsl 只渲染一条**：把 `for-each` 的过滤条件 `[link='https://luowenpeng.com/about']` 改成遍历全部 `item`，并补上日期与摘要的展示。
3. **无日期条目混入**：`about.md` 没有 `date` frontmatter，生成的 item 缺 `pubDate`，RSS 阅读器无法正确排序。在 `generate-rss.mjs` 里加了一道过滤。

第 3 点不在原问题清单里，是修第 2 点时顺手发现的——**修一个 bug 时把相邻的一段代码读完整，往往能捞到额外的**。

### 3.3 清理失效组件与重复配置

- **不蒜子**：删掉 `Busuanzi.vue`、主题里的挂载、以及 `custom.css` 里 19 行样式，只留 GoatCounter。两套统计本来就重复，又有一套是坏的。
- **空分组**：删除 `GuidedReading` 整个块。
- **版权版本**：README 与 `index.md` 的 3.0 链接统一改成 4.0，与 `LICENSE` 一致。
- **双份 `CNAME` / `.nojekyll`**：**这里翻了车**，详见第四节。

### 3.4 两个子站接回主站

这两个页面（`analogy-collection.html`、`metro-passenger-flow.html`）放在 `docs/public/` 下，是纯静态产物，**不参与 VitePress 路由**，所以既没有站内导航、也不在搜索索引里、更没有统计。给它们各补了：返回主站导航条、canonical、OG/Twitter、GoatCounter。

其中一个必须**改在别的地方**：

```
analogycollection 仓库 --(workflow 同步)--> 本仓库 docs/public/ --> 部署上线
```

`sync-to-blog.yml` 监听 `analogycollection` 的 `main` 分支，一旦推送就把两个文件**覆盖**过来。所以在本仓库改 `analogy-collection.html` 是无效的，下次同步会被冲掉——得改源头。

这类「跨仓库同步的内容」最容易被误伤，解决办法是在 README 里显式写死警告：

> ⚠️ `docs/public/analogy-collection.html` 与 `analogy-data.js` 是外部推送进来的产物。需要改样式或结构时请到 `analogycollection` 仓库改，直接改本仓库文件会在下次同步时被静默覆盖。

### 3.5 工程化补充

- ECharts 加 SRI（`integrity` + `crossorigin`），并在 CDN 失效时用一段小脚本显示可见提示，而不是留一片空白。哈希要自己算两次确认稳定：`openssl dgst -sha384 -binary f.js | openssl base64 -A`。
- `gen-og-image.py` 的输出路径改成命令行参数、默认取仓库内相对路径；顺带把同样写死的 Windows 字体路径改成跨平台候选列表——只改一半的话脚本仍然是「只能在我这台机器上跑」。
- 新增 `.github/dependabot.yml`，覆盖 npm 与 github-actions，按月更新并给 VitePress 相关依赖分组。

### 3.6 移除 feed 的 XSLT

最后一件事来自一条浏览器提示：打开 `feed.xml` 时显示「此网站使用 XSLT；该功能将即将从此浏览器中移除」。

**先判断性质**：这不是站点故障，是 Chrome 面向所有网站的通用政策公告。触发它的只是 feed 里那行 `<?xml-stylesheet?>`。关键事实是——RSS 阅读器直接解析 XML，从不跑 XSLT，**订阅者完全不受影响**；Chrome 目前也仍在渲染，只是多一条横幅。

所以这是个取舍而非 bug。最终选择移除，理由是一句话：**feed.xml 本来就是给机器读的，为人类准备的入口应当是站点页面**。与其依赖一项即将被移除的技术去美化一个机器接口，不如让它回归纯粹。改了两处：`generate-rss.mjs` 不再输出该处理指令，删除 `rss.xsl`（git 历史可随时取回）。

## 四、事故：我亲手把站点搞挂了 20 分钟

这一节是全篇最值钱的部分。

### 4.1 时间线

推送第一批改动后去做线上验证，发现 `https://luowenpeng.com` **全线 404**，所有路径都返回 GitHub Pages 的错误页。而同一时刻 `https://luowenpeng.github.io` 完全正常，且已经是新内容。

排查过程按层展开：

1. **DNS 是否正常** → `nslookup` 返回 `185.199.108~111.153`，是 GitHub Pages 的正确 IP，正常。
2. **站点是否真的部署了** → 查 Actions API：`Deploy VitePress site to GitHub Pages` 与 `pages build and deployment` **双双 success**。CI 全绿，站点却打不开。
3. **域名是否还绑着** → `http://luowenpeng.github.io/CNAME` 返回 301 跳转，说明关联还在；但访问自定义域名的任何路径都 404。
4. **定位到自己的改动** → 这批改动里唯一与域名相关的，就是我删掉了根目录的 `CNAME` 与 `.nojekyll`。

恢复 `CNAME` 后，域名解析回来了，但换了个更诡异的现象：页面标题变成 `luowenpeng.github.io | luowenpeng`，内容是 Jekyll 渲染的 README，生成器写着 `Jekyll v3.10.0`——**因为 `.nojekyll` 也被我删了**。再把 `.nojekyll` 补回来，站点才彻底恢复正常。前后中断约 20 分钟。

### 4.2 我的判断错在哪

当时的推理是：「Actions 制品部署只认 `docs/public/CNAME`，根目录那两份是死配置，留着只会误导人」。这个推理**前半句对，结论错**。

对的部分：真正随制品发布的确实是 `docs/public/CNAME`。

错的部分：「死配置」这个判断。它们是**保险丝**，不是垃圾：

- 删 `CNAME` → GitHub 认为你不要这个自定义域名了，直接解绑。
- 删 `.nojekyll` → 一旦 GitHub 因任何原因改按分支源构建，就会启动 Jekyll 处理仓库根目录，把 `README.md` 渲染成首页。

更隐蔽的是，**CI 完全不会报警**。`deploy.yml` 成功了，制品也上传了，只是域名没了。构建成功和站点可访问是两件事。

### 4.3 三条教训

1. **删除任何配置文件前，先问一句「这个文件谁在读」。** 尤其是那些看起来多余、重复、年代久远的——它们常常是某次事故留下的保险。删除的收益是「少一个文件」，风险是「整站下线」，完全不成比例。
2. **CI 全绿不等于站点正常。** 构建成功只说明产物生成了，不说明域名、证书、DNS 还在工作。上线后必须真的去访问，而且要访问**自定义域名**，不只是 `*.github.io`。
3. **判断「死配置」要有证据，不能靠推理。** 事后我在 README 里写死了警告，把这个坑固化下来：

   > 不要删除根目录的 `CNAME` 与 `.nojekyll`。随制品发布的是 `docs/public/CNAME`，但根目录这两份是 GitHub 侧的保险：两者任一缺失，GitHub 会解绑自定义域名或退回用 Jekyll 渲染仓库根目录，站点会直接 404。

## 五、经验沉淀

### 5.1 六条可迁移的经验

1. **先判断性质，再动手。** 今天遇到两类「问题」：一类是真 bug（OG 写死、xsl 过滤条件），一类是外部政策变化（Chrome 弃用 XSLT）。后者不需要修 bug，只需要做取舍——把性质分清，能省掉一半无用功。
2. **单一事实源，其余全部引用。** 同一份文章清单抄了四遍，就必然漂移。现在文章清单的权威只有 `config.ts` 与各专题页，README 改为只写仓库操作和管线说明。
3. **站端有四类「仓库里看不见」的设置。** 自定义域名、HTTPS 强制、仓库 homepage/topics、Secrets。它们不会出现在任何文件里，却直接决定站点能不能访问。换环境、换机器时最容易漏的就是这一层。
4. **外部依赖都要留后路。** 统计服务会挂（不蒜子）、CDN 会抽风（ECharts）、浏览器会移除能力（XSLT）。凡是链到别人家的东西，都要问一句「它没了会怎样」。
5. **分享卡片是门面。** 文章写得再好，分享出去显示的是站名和一张通用封面，转化就断在最后一步。`transformHead` 这种按页生成元信息的钩子，成本极低、收益极高。
6. **上线后必须验证，而且验证的是用户实际访问的路径。** 见下方清单。

### 5.2 上线后验证清单

这次能及时发现事故，靠的就是这张表。以后每次改动部署完都过一遍：

| 层级 | 检查 | 方法 |
|---|---|---|
| 域名 | 自定义域名可访问 | 直接访问 `https://你的域名/`，**不要只测 `*.github.io`** |
| 协议 | HTTP 跳 HTTPS、有 HSTS 头 | `curl -I http://域名` 看 301；响应头找 `strict-transport-security` |
| 构建 | Actions 全绿 | 看 `deploy.yml` 与 `pages build and deployment` 双 success |
| 内容 | 新文章真的上线 | 抓页面看 `<title>` 与正文关键词 |
| 元数据 | OG/canonical 按页生成 | 抓 HTML 搜 `og:title` 是否与文章标题一致 |
| 订阅 | feed 可解析、条目数正确 | 用 XML 解析器读一遍，别只看浏览器 |
| 资源 | 外部脚本可达 | 对 CDN 依赖单独探活 |

> **最关键的一条**：CI 绿只说明「产物生成了」，不说明「用户能打开」。这两件事之间隔着域名、证书、DNS 三层。

### 5.3 排查方法本身也值得记录

这次定位问题用的是**对照法**：把仓库侧的事实（文件、配置、脚本）和线上侧的事实（HTTP 响应、响应头、sitemap）各列一遍，两边对不上就是问题所在。

| 仓库侧可查 | 线上侧可查 |
|---|---|
| `config.ts` 的导航/侧边栏链接 | sitemap.xml 的 URL 全集 |
| md 文件清单与 frontmatter | 每个 URL 的实际状态码 |
| 脚本生成的产物（feed、og） | 页面的 `<head>` 实际内容 |
| workflow 定义 | Actions 运行记录与 conclusion |

对照法的好处是不依赖任何猜测——今天所有结论都有实测数据兜底，包括「哪条是死配置」这类差点判断错的地方。

## 六、结果与遗留

| 项 | 数量 |
|---|---|
| 查出问题 | 16 |
| 本次修复并上线 | 12 |
| 站端手动完成（HTTPS 强制、仓库元数据） | 2 |
| 主动搁置 | 2 |

**主动搁置的两项**，都是收益不够抵成本的：

- 图片转 WebP：`docs/public/images` 共 2.7MB，最大单图 236KB，当前不影响加载体验，属于锦上添花。
- 功能台账更新：`网站功能台账-Feature-Ledger.md` 里「无 404 页、无归档页」等结论已与现状不符，但整篇重写成本高，暂记一笔。

**结构性遗留一项**：类比库页面的源码在 `analogycollection` 仓库，本仓库那份不可手改。这是跨仓库同步架构决定的，已用 README 警告兜住。
